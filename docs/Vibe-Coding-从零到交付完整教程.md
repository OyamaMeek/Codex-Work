# Vibe Coding 从零到交付完整教程

这份教程带你完成一次完整的 AI 辅助开发。你用自然语言描述需求，让 AI 编写和修改代码，再通过运行、测试和审查判断结果。读完后，你应该能发起一个小项目，处理开发中的报错，保存可恢复的版本，并把成果交给别人使用。

全文用一个“个人待办网页”练习。它是一项教学任务，本文没有替你创建或运行这个程序。提示词可以直接复制到编程代理中，也可以替换成你的项目需求。

我核对了本地 AI-Coding-Guide-Zh 的任务描述、Review、实战和上下文管理内容，并参考了 OpenAI 官方文档。界面入口可能变化，因此步骤主要使用自然语言，不依赖特定按钮或命令名称。

## 1. 先认识你要负责的事情

AI 可以读取代码、修改文件、执行命令，也可能误解需求或漏掉边界。你可以把具体实现交给它，同时保留对产品目标和验收结果的判断。

| 你需要做的事 | AI 可以协助完成的事 | 用什么判断结果 |
| --- | --- | --- |
| 说明给谁用、解决什么问题 | 整理需求和疑问 | 需求是否符合你的实际用途 |
| 确定第一版的范围 | 提出实现计划 | 功能、文件和依赖是否合理 |
| 提供项目资料与报错 | 阅读代码、定位原因 | 引用的文件与错误是否真实存在 |
| 试用并描述问题 | 编写代码、修复缺陷 | 操作结果与测试结果 |
| 决定是否交付 | 整理文档、提交和发布准备 | 新使用者能否照说明运行 |

遇到这些词时，先记住它们在流程里的作用。

| 词语 | 在本教程里的含义 |
| --- | --- |
| 项目目录 | 当前项目的文件夹，决定 AI 正在操作哪一份文件 |
| 前端 | 浏览器里看见的页面和交互 |
| 后端 | 在服务器上执行的数据处理和业务逻辑 |
| 依赖 | 项目使用的外部代码库或工具 |
| 终端 | 输入和运行命令的地方 |
| 日志 | 程序执行时输出的信息和错误 |
| diff | 修改前后文件的差异 |
| 测试 | 用明确的输入和预期结果检查行为 |
| Git commit | 保存一组代码改动及说明的版本记录 |
| 部署 | 把程序放到目标运行环境，使其他人能够访问 |

你可以暂时不熟悉语法，但需要知道项目从哪里运行、数据存在哪里、修改了哪些文件，以及怎样证明功能可用。

## 2. 准备一个明确的工作目录

你现在已经在 Codex 中，可以继续使用现有工具。先为练习准备一个独立目录，例如 `vibe-todo`。在编程工具中选择这个目录作为项目，再确认代理看到的路径。

如果你准备修改已有项目，直接打开它的真实目录。保留原有文件、依赖和运行方式，先读取项目说明。不要把生产数据或账号凭据当作练习素材。

第一次进入目录，发送下面的提示词。

```text
请先确认当前项目目录的绝对路径。
读取已有 README、项目配置和适用的项目指令。
告诉我现有文件、使用的语言、运行命令、测试命令，以及这些结论来自哪里。
如果目录为空，明确说明。
这一步只读取，不修改文件，不安装依赖，不初始化 Git。
```

**完成标准**

- AI 给出的路径与目标目录一致。
- 已有项目的运行方式可以追溯到实际文件。
- 空目录被明确识别，没有编造现成代码或命令。

如果工具提示没有读取或写入权限，让它指出具体路径和被拒绝的操作。按任务需要授权，确认工作目录后继续。项目访问权限与外部账号授权需要分别判断。

## 3. 把想法写成第一版需求

先描述一个用户能完成的动作。第一版的目标越清楚，后续越容易判断改动是否必要。

可以使用这个句式。

```text
我想做一个【工具】，给【使用者】使用，帮助他们【解决问题】。
第一版需要【核心功能】。
这次不包含【明确排除的功能】。
当【可观察结果】成立时，这个版本算完成。
```

本教程采用下面的练习需求。

```text
我要做一个个人待办网页，给自己记录学习任务。

第一版需要
1. 输入任务名称并添加到列表。
2. 将任务标记为完成，也能恢复为未完成。
3. 删除单条任务。
4. 刷新页面后保留任务与完成状态。

空白名称不能添加。任务名称按普通文字显示。
没有任务时显示提示，保存失败时给出明确反馈。
页面能在电脑和手机宽度下正常使用，并支持键盘操作。

这次不做登录、多人共享、云端同步和付费功能。
数据保存在当前浏览器中，这个限制需要写进使用说明。
```

这里已经决定了一件具体产品行为。刷新后保留记录，需要持久保存任务；当前浏览器保存又明确了它的使用范围。AI 据此实现，你据此验收。

以后修改需求，也要写清变化。例如“第一版增加任务搜索，输入关键词只筛选显示，不删除原有任务”。

## 4. 先写验收方法

在生成代码前，先把你打算怎样试用写下来。验收方法能让 AI 知道完成条件，也能防止你只凭页面出现了就认为任务结束。

| 操作 | 预期结果 |
| --- | --- |
| 首次打开页面 | 显示空列表提示 |
| 添加“学习英语” | 列表出现一条对应任务 |
| 输入空格并添加 | 不产生任务，出现适当提示 |
| 标记任务完成 | 完成状态可辨认，刷新后仍保留 |
| 恢复任务为未完成 | 状态恢复，刷新后仍保留 |
| 添加两条任务，再删除其中一条 | 只删除目标任务 |
| 输入包含 `<` 和 `>` 的文字 | 作为文字显示，不被解释成页面代码 |
| 刷新或重新打开同一地址 | 保留已保存的数据 |
| 用 Tab 移动并用键盘操作 | 可以使用主要控件，焦点可见 |
| 在手机宽度使用 | 内容可读，按钮能够操作 |

把这些要求交给 AI。

```text
请根据上述需求整理验收清单。
分别写正常操作、无效输入和保存失败时的预期行为。
列出哪些检查可以自动运行，哪些需要实际操作页面。
目前只整理，不写应用代码。
```

**完成标准**是每个核心功能都有具体操作和预期结果，错误情况也有明确行为。这里的清单是待执行的检查，不能提前标记通过。

## 5. 决定实现方式和执行顺序

对于这个单人、单页、没有服务器业务的练习，可以从 HTML、CSS 和 JavaScript 开始。已有项目则优先使用现有实现方式。需要账号、跨设备数据或服务器处理的项目，要另外设计后端和数据存储。

计划应说明会创建或修改哪些文件、如何保存数据，以及如何运行。OpenAI 官方文档建议为任务提供目标、上下文、约束和完成条件；复杂或含糊的任务适合先制定计划。[官方任务与规划建议](https://learn.chatgpt.com/guides/best-practices)

```text
请为个人待办网页制定实现计划，先不要执行。

如果目录为空，使用 HTML、CSS、JavaScript 和浏览器本地存储。
如果目录已有项目，先说明如何复用现有结构。

计划需要说明
1. 会创建或修改哪些文件。
2. 任务有哪些数据字段。
3. 添加、修改状态、删除与保存的流程。
4. 怎样处理无效输入和保存失败。
5. 启动方式与适用的验证方法。

按可以独立运行和验证的步骤拆分。
不添加需求外的功能；有影响实现的歧义就明确指出。
```

检查计划时，重点看是否遗漏已约定功能，是否引入了没有用途的依赖，以及数据保存方式是否满足实际用途。

这个练习可以按下面的顺序执行。

| 阶段 | 做完后能验证什么 |
| --- | --- |
| 添加和显示 | 用户输入能够变成列表中的任务 |
| 完成状态与删除 | 每次操作只影响对应任务 |
| 持久保存与错误反馈 | 刷新后保留记录，保存异常有明确提示 |
| 使用体验与交付 | 键盘和不同宽度可用，说明足够清楚 |

每个阶段都要完成实施和验证，最后仍然交付全部约定功能。

## 6. 给出可以执行的指令

计划确认后，把执行范围写清楚。不要让 AI 在同一轮猜测产品需求、搭建大量基础设施并完成全部扩展功能。

```text
按刚才确认的计划执行第一阶段，完成添加和显示任务。

范围
只创建这个阶段需要的文件，沿用已有项目模式。
不要混入完成状态、删除、账号或云端功能。

要求
空白任务不能添加，任务文字按普通文本显示。
先添加或找到能够检查这两个行为的最小测试，确认目标问题尚未满足。
实现后运行相关检查，修正问题直到通过。
已有测试工具优先复用，不为这个练习搭建复杂测试体系。

交付
告诉我修改的文件、启动方式、实际运行的检查及结果。
没有执行的检查要明确说明。
Git 操作遵守当前项目已约定的规则。
```

同一个目标可以在一个聊天中继续完成。阶段结束后核验结果，再让 AI 执行下一阶段。不同且无关的目标可以另开聊天，避免上下文混在一起。

添加和显示通过后，继续完成状态修改与删除。

```text
第一阶段已经按验收清单核验，请继续实现完成状态切换和单条删除。
每条任务需要能够被准确识别，操作只能影响目标任务。
覆盖两条同名任务、切换后再切回，以及删除其中一条的情况。
保留已有添加行为，运行相关检查并报告实际结果。
这一步完成后，继续按第9节实现持久保存。
```

**完成标准**是实际文件已经改变，当前阶段可以运行，相关检查有真实结果。AI 的完成总结需要与文件、命令输出对应。

## 7. 把程序真正运行起来

让 AI 根据项目实际情况启动程序，给出明确访问地址。如果已有 `package.json` 或其他配置，读取其中的命令再运行，不能默认任何项目都有 `npm run dev`。

```text
请根据项目实际文件确认运行方式。
检查所需运行环境是否已安装，使用已有依赖和命令启动项目。
给出工作目录、启动命令、访问地址和停止方式。
如果启动失败，保留原始报错并定位原因，不要把启动尝试写成成功。
```

对于纯静态练习，如果电脑已有 Python 3，可以在练习目录运行下面的本地服务器。

```bash
python3 --version
python3 -m http.server 8000 --bind 127.0.0.1
```

命令需要按顺序执行。先确认 Python 3 可用，再启动服务器，然后在浏览器打开 `http://127.0.0.1:8000/`。如果页面文件为 `index.html`，通常会显示它；若显示目录列表，检查入口文件是否存在。结束时在运行服务器的终端按 `Ctrl+C`。

这个服务器用于本机开发检查。端口被占用时，先确认占用情况再选择可用端口，并重新记录访问地址。没有 Python 时，让 AI 检查现有项目工具提供的静态服务器；安装新工具前说明必要性。

练习涉及本地存储，因此使用固定的 HTTP 地址进行验证。直接双击 HTML 文件产生的 `file:` 地址，其本地存储行为没有统一保证。[MDN 本地存储说明](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)

**完成标准**是进程实际运行，访问地址可以打开正确页面，基本操作有响应。页面能打开后，还需要逐项检查业务行为。

## 8. 学会描述问题和处理报错

给 AI 的反馈尽量包含你的操作、预期结果、实际结果和原始错误。提供真实失败过程，比只说“有问题”更容易定位原因。

下面是一份假设的缺陷报告格式，可以按实际情况替换。

```text
问题发生在删除任务时。

复现步骤
1. 添加任务 A。
2. 添加任务 B。
3. 点击任务 A 的删除按钮。

预期结果
只删除任务 A，任务 B 保留。

实际结果
任务 B 也消失了。

请先沿删除事件、任务标识和列表更新流程定位根因。
添加能复现问题的最小测试，确认失败后再修复。
完成后重新运行相关检查，不扩大到无关重构。
```

程序无法启动时，提供终端报错。页面交互异常时，可以打开浏览器开发者工具的 Console，复制与失败相关的错误，同时保留文件位置和错误堆叠。提交内容前去掉账号凭据和隐私信息。

有截图或视觉验证需要时，在任务里明确说明页面、尺寸和期望结果。先取得页面实际状态，再根据观察修改样式。

常见情况可以按下面的顺序检查。

| 表现 | 先检查什么 |
| --- | --- |
| 启动命令不存在 | 当前目录与项目配置中的真实命令 |
| 页面空白 | 入口文件、资源加载和浏览器错误 |
| 按钮没有反应 | 事件是否绑定，是否发生运行时错误 |
| 刷新后数据消失 | 保存与读取流程、访问地址是否变化 |
| 修改了代码却没有变化 | 是否访问正确项目，资源是否更新 |
| 装依赖后仍失败 | 实际报错、依赖版本和项目要求 |

同一问题连续修复两次仍然失败，就停止重复尝试。

```text
这两次修改没有解决问题。
请重新从入口读取相关流程，检查之前的假设。
列出已证实的事实和仍需验证的原因。
先运行一个能区分这些原因的检查，再选择修复位置。
```

**完成标准**是原来的复现步骤已经通过，同时相关原有功能继续可用。仅仅换掉报错文字或删除失败检查，不足以证明修复完成。

## 9. 完成持久保存，理解数据在哪里

要求“刷新后保留任务”时，AI 需要实现保存和恢复流程。任务至少要能够区分身份、名称和完成状态，具体字段由实现方案确定。

```text
请按计划实现任务持久保存。
添加、修改完成状态、删除后，都应保存当前数据。
打开页面时恢复任务及状态。
空记录、数据格式异常和无法保存时需要有明确处理。
读取到异常数据时保留可诊断信息，不要直接覆盖并抹掉旧内容。
运行适用检查，并告诉我浏览器数据的存储范围。
```

这个练习使用浏览器 `localStorage`。它与访问来源有关，协议、主机或端口改变后，读取的数据范围可能改变。直接使用本地文件地址也有兼容性限制。[MDN Web Storage 范围说明](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API)

因此，你需要把下面的使用限制写进 README。

- 数据保存在当前浏览器的当前来源中。
- 换浏览器、换设备或改变访问地址，可能看不到原有记录。
- 清除浏览器站点数据会删除对应保存内容。
- 无痕或隐私窗口中的记录可能在关闭窗口后消失。
- 重要记录需要另行设计备份或导出能力。

如果需求已经变成“手机和电脑都能看到同一批任务”，需要重新讨论账号、服务端存储和同步。这是产品范围变化，应先设计再实现。

**完成标准**是添加、状态修改和删除经过刷新后仍然正确，异常情况下有明确反馈，使用说明准确反映保存能力。

## 10. 运行测试，再审查改动

验证可以分成程序检查与用户操作检查。语法、类型、构建和自动化测试各有用途，适用命令应从项目配置中读取。对于简单静态页面，不能为凑检查数量而宣称不存在的类型检查通过。

```text
请对当前阶段做验证和审查。

先读取项目配置，确定适用的测试、构建和静态检查。
运行必要检查，逐项给出实际命令、结果和未覆盖范围。
检查 diff 是否包含需求外功能、无关文件改动或敏感信息。
对照验收清单检查核心行为和错误处理。
报告实际问题；没有执行的用户操作检查保留未验证状态。
```

查看 diff 时，至少弄清修改了哪些文件，以及为什么需要这些改动。看不懂某段代码，可以让 AI 解释输入、输出和改变后的行为。

```text
请解释这次改动中任务保存的流程。
说明它接收什么数据、写入哪里、哪些操作会触发保存。
指出保存失败与旧数据异常时的处理。
只解释当前代码，不继续修改。
```

OpenAI 官方文档将测试、最终行为确认和 diff 审查列为可靠性检查的一部分；提示词或项目指令应说明怎样判断结果。[官方测试与审查建议](https://learn.chatgpt.com/guides/best-practices)

**完成标准**是必要检查通过，已发现问题得到处理，剩余未验证范围被如实记录。AI 自己审查的结论也需要与测试和实际行为结合判断。

## 11. 逐项验收使用体验

现在按第4节的表格实际使用页面，记录每项结果。不要只检查正常添加，也要检查删除目标、空白输入、刷新恢复和键盘操作。

调整界面时，把反馈写成具体变化。

```text
只调整待办页面的使用体验，不修改任务数据和保存逻辑。

要求
主要内容在电脑上居中，宽度适合阅读。
手机宽度下输入框和按钮不会挤出页面。
完成状态有文字或控件提示，不只靠颜色区分。
输入框有可识别的名称，键盘焦点可见。

完成后运行适用检查，再确认添加、完成、删除和刷新恢复没有受到影响。
```

如果要求 AI 执行视觉验证，要明确授权它打开页面和检查图像。验证记录应包含页面地址、视口尺寸和观察结果。没有视觉证据时，它只能说明已经完成代码和行为检查，不能声称某个尺寸的页面已看过。

**完成标准**是约定的操作可用，文字与控件可读，键盘能够完成主要操作，而且界面修改没有破坏数据行为。

## 12. 用 Git 保存可以恢复的版本

项目有 Git 时，可以把一个已经通过验证的功能阶段保存为 commit。Git 保存代码版本，浏览器中的待办数据需要另外处理。

先检查当前状态。

```bash
git status --short
git diff
```

这两条命令用于读取状态。看到未提交文件时，先弄清哪些属于本次任务，哪些是原有工作。提交前检查凭据、配置与生成文件，暂存本次需要保存的具体文件。

下面的命令适用于示例文件已经存在、确认属于本次工作、当前没有其他不该提交的暂存内容，并且身份和提交规则已经配置好的情况。

```bash
git add index.html styles.css app.js README.md
git diff --cached --check
git diff --cached
git commit -m "feat: add personal todo page"
```

文件名需要按真实项目调整。如果检查失败，先修正再继续。不要把这些命令当作必须逐字执行的固定模板。

也可以直接请 AI 操作。

```text
请先检查 Git 状态和暂存区。
确认本次功能已通过适用验证，只暂存本次任务的文件。
保留其他人的修改，检查提交内容后创建一个说明清楚的 commit。
推送按当前项目已经授权的规则执行，不强制推送，不改变远端目标。
```

如果目录没有 Git，先决定是否需要版本管理，再明确授权初始化。已有仓库不需要重新初始化。删除工作内容或恢复旧版本前，先确认恢复点和受影响文件，避免覆盖未保存的修改。

本工作空间已经约定自动提交、普通推送和保留日志。练习中的 Git 操作应遵守该约定。进入其他项目时，按对应项目的授权规则处理。

**完成标准**是 commit 中只包含本次改动，说明准确。执行了推送时，还要确认远端接收成功。

## 13. 增加功能时重新走一遍小循环

第一版验收后，可以增加搜索、分类或其他确有用途的功能。每次明确一个行为变化，并保留原有验收方法。

例如新增搜索功能。

```text
目标
给待办网页增加任务名称搜索。

行为
输入关键词后，只显示名称包含关键词的任务。
清空关键词后，恢复显示全部任务。
筛选只影响显示，不修改保存的任务数据。
在筛选结果中完成或删除任务时，只影响对应任务。

范围
复用现有页面和保存逻辑，不新增账号、分类或依赖。

验证
覆盖有匹配、无匹配、清空关键词，以及筛选后修改任务的行为。
实现后重新检查第一版的核心功能。
```

**完成标准**是新行为成立，原来已经可用的功能仍然通过。需要改动数据格式时，计划还要说明旧数据如何继续读取，不能把旧记录丢掉作为升级方式。

## 14. 在长任务中保留有效上下文

聊天里讨论过的决定，适合简洁地保存在项目文件中。小项目通常先有 README 就够用；出现多个阶段和待解决问题后，再增加进度记录。

| 文件 | 适合记录的内容 |
| --- | --- |
| `README.md` | 项目用途、运行步骤、数据位置、已知限制 |
| `AGENTS.md` | 代理需要遵守的项目规则、真实验证命令和重要约束 |
| `memory/progress.md` | 已完成事项、验证结果、剩余问题和下一步 |

Codex 会读取适用的 `AGENTS.md` 项目指令。规则应当与实际项目一致，写明可核验的运行和检查方式。[官方项目指令说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

在新项目中，一个简短的指令文件可以包含以下内容。已有指令先读取并遵守，不直接覆盖。

```markdown
# 项目协作规则

- 优先复用现有代码和依赖，保持当前命名与结构。
- 修改前读取相关实现，保留用户已有改动。
- 每次完成约定功能并运行适用检查。
- 验证命令从项目配置确认，不编造成功结果。
- 不把账号凭据、隐私数据和临时调试文件加入提交。
- Git 与外部写操作遵守当前已经授权的范围。
- 完成阶段后更新 README 和进度记录。
```

准备换聊天继续时，可以发送下面的提示词。

```text
请把当前项目状态写进进度记录。
包含原始目标、已完成功能、改动文件、实际验证结果、剩余问题和下一步。
保留影响后续实现的决定，删除已失效的状态说明。
给出新聊天开始时应该先读取的文件。
```

新聊天先读取这些记录和相关代码，再继续修改。不要依赖“上次聊过”的口头指代。

**完成标准**是另一位协作者读取项目记录后，能知道如何运行、已经验证到哪里，以及接下来该处理什么。

## 15. 按新使用者的路径交付

交付前，把自己当成第一次拿到项目的人。先读 README，按说明准备环境、运行程序，再完成核心操作。

```text
请检查这个项目是否可以交给新使用者。

核对 README 中的环境要求和运行步骤是否与真实项目一致。
按新使用者路径验证核心功能，并记录实际结果。
说明数据保存位置、功能限制和停止方式。
对未完成的检查明确标记，不发布、不上传外部服务。
```

README 至少应回答这些问题。

- 项目能做什么，主要给谁使用。
- 需要什么环境，怎样启动和停止。
- 用户怎样完成核心操作。
- 数据存在哪里，怎样避免误删。
- 哪些能力尚未提供。

对于待办练习，本地运行并交付文件已经是一种完整成果。希望别人通过网址访问时，再进入部署阶段。

## 16. 需要发布时，先确认目标环境

静态页面可以部署到支持静态文件的托管环境。带后端的项目还需要处理服务运行、配置、数据库和故障恢复。托管服务的价格、限制和界面会变化，应按选定平台的当前官方文档执行。

```text
我要准备发布这个项目，先不要执行发布。
请确认它属于静态网站还是需要后端服务。
根据我指定的目标平台，读取当前官方部署文档。
列出构建或上传内容、环境配置、数据位置、费用相关条件和恢复方式。
在本地完成必要的发布前检查，给出可审查的结果。
```

确认具体发布目标和准备结果后，再授权发布。

```text
按已确认的目标环境执行发布。
发布后访问实际地址，重新验证核心操作和资源加载。
报告发布结果、版本、验证范围以及出现问题时的恢复方法。
```

对本教程的待办页，即使代码公开到网址，任务记录仍然保存在各自浏览器中。公开页面不会自动增加账号或跨设备同步。

后续如果接入服务器 API，应把密钥留在服务器配置中，给输入和权限增加实际校验，并为请求失败设计反馈。发生收费或写入重要数据的请求，还需要明确防止重复操作的方法。

**完成标准**是目标地址实际可访问，发布后的核心行为经过验证，数据范围和恢复方式已经记录。

## 17. 什么时候学习扩展能力

先完成一个能运行、能验证、能保存版本的小项目。之后再根据实际阻碍补充工具。

| 能力 | 适合解决的具体问题 |
| --- | --- |
| Skill | 重复执行同一套开发或审查步骤，希望复用指令与资源 |
| MCP | 需要让代理读取或操作外部工具和实时资料 |
| Plugin | 需要安装一组相关技能、工具或连接能力 |
| Subagent | 有可以独立处理的工作，需要明确分工与汇总检查 |
| Worktree | 多个任务要在隔离的 Git 工作目录中进行 |
| Automation | 已有稳定、明确的检查，想按时间或事件重复执行 |

这些能力需要各自的上下文、权限和验证方法。不要用工具数量判断项目成熟程度。是否需要某项能力，应由当前任务中的具体问题决定。

本地 AI-Coding-Guide-Zh 已有对应章节，可以按问题查阅。Codex 的 CX-02 讲工作流，CX-04 讲项目指令与权限，CX-05 至 CX-09 分别讲外部工具、Skills、Plugins、Subagents 和 Automations。

## 18. 一份可以直接复制的完整开工提示词

下面把前面的要求合并成一份起始任务。空目录可以直接使用；已有项目先要求 AI 复用项目现状。

```text
我要做一个个人待办网页，用来记录学习任务。

第一版功能
添加任务、切换完成状态、删除单条任务、刷新后恢复记录。
拒绝空白任务，任务名称按普通文本显示。
空列表和保存失败有明确提示。
支持键盘操作，电脑与手机宽度可用。
不包含登录、云端同步或多人共享。

开始前
确认当前目录，读取已有文件和适用的项目指令。
如果已有项目，复用现有结构与依赖。
如果目录为空，采用 HTML、CSS、JavaScript 和浏览器本地存储。
先整理验收清单与实现计划，说明文件、数据流、运行和检查方式。
计划得到确认后再执行。

实施要求
按可以独立运行和验证的阶段完成全部约定功能。
非简单逻辑和缺陷修复需要最小有效检查，保留真实失败与通过结果。
发生问题时沿实际流程定位根因，不混入无关重构。
不抹掉已有任务数据，不修改范围外文件。
实际运行验证；无法运行的部分明确说明原因。

交付要求
给出修改文件、访问方式、实际检查结果和未覆盖范围。
更新 README，说明本地存储范围与限制。
检查 diff，Git 操作按当前项目既有授权执行。
外部发布需要我明确指定目标并授权。
```

## 19. 完成一次练习的验收清单

- [ ] 可以用一句话讲清项目给谁用、解决什么问题。
- [ ] 第一版包含哪些功能已经明确。
- [ ] 工作目录、入口文件和启动方式已核对。
- [ ] 核心功能和失败情况有具体验收方法。
- [ ] 程序实际运行，相关检查有真实结果。
- [ ] 添加、状态修改、删除和刷新恢复可用。
- [ ] 已检查键盘操作和约定的页面宽度。
- [ ] 了解数据保存位置和清除数据的后果。
- [ ] 已审查本次文件差异并处理发现的问题。
- [ ] README 足以让新使用者运行项目。
- [ ] 代码版本已按项目规则保存。
- [ ] 如果发布，目标地址和核心行为已验证。

这些项目需要在实际练习后填写。教程写完不代表已经完成项目，也不代表已经确认掌握全部概念。
